# ops-batch MCP —— 设计文档

日期：2026-10-15
状态：待批准

## 意图与缘起

在 Claude Code 里自用。动机是单一且朴素的：**每个任务都会烧掉很多 token**。目标是让账单真正降下来，不是移植 dsh-ops。

dsh-ops（`T-Auto/dsh-ops`）是 DSH 宿主的插件，用 Rust 重写文件检索与批处理，把宿主自带的 read/grep/glob/edit/bash 换成一组 `ops_` 工具，号称对照 Windows 标准模式省 97% token。但它有四分之三的能力绑在 DSH 宿主、沙箱权限和 Rust worker 上，做 MCP 版只能保留"省 token 的交互形态"。

## 证据：账单到底花在哪

对 `C:\Users\Lenovo\.claude\projects\D--guet-agent---\` 下 22 个会话转录（210 MB）做了三轮统计。样本是本机 guet-agent 项目的全部历史。

**工具调用量**

| 工具 | 次数 |
| --- | --- |
| Bash | 5,298 |
| Edit | 2,056 |
| Read | 814 |
| Write | 655 |
| Grep / Glob | 97 / 27 |

**原始字符量**

| 内容 | 字符 | 说明 |
| --- | --- | --- |
| 工具结果 | 9.40M | cache write，单价高 |
| thinking | 15.14M | 比全部工具结果加起来还多 |
| 工具参数（模型写的 JSON） | 9.23M | Bash 3.2M / Write 3.1M / Edit 2.5M |
| 助手正文 | 2.14M | |

**按工具分的工具结果占比**：Bash 51.8%（5,298 次，均值 920 字符），Read 37.2%（仅 814 次，均值 4,297 字符——单次最贵），其余合计 <5%。

**结论一：输出 token（想 + 写）是大头，不是读进来的内容。** 这恰好是 dsh-ops 自己讲的动机——报错循环、强迫思考不交付、注意力涣散。

**结论二：没有任何一条工具结果超过 60K 字符。** 22 个会话里一条都没有。

**结论三：重复调用普遍。** Bash/Read/Grep/Glob 里 18.4% 的调用是之前某次调用的逐字重复（MEMORY.md 读 13 次、config.py 读 8 次、llm_client.py 共读 31 次）。但重复的往往是小结果，按字符量折算的占比明显低于 18.4%。

**结论四：三个具体浪费模式**

1. 678 次 Bash 带着同一串 SSH 前导（`export GUET_SSH_PASS=… && ssh -p … && source … && cd …`），每次由模型重写三百多字符。
2. 392 次 sleep 轮询，累计 1,273 分钟挂钟时间。这是时间不是 token，且更像 hooks/CLAUDE.md 能治的。
3. 编辑高度集中：WORK_PROGRESS.md 89 次、CLAUDE.md 48 次。

**一处必须记录的更正**：早期统计给出过"约 180 亿字符·轮"的说法，那是**上界且偏大**——它假设历史永远留在上下文里，而这些会话明显做过 compact；也忽略了 prompt caching 让稳定前缀按 10% 计价。该数字不可引用，上述四张表才是。

**样本局限**：全部证据来自 guet-agent 一个项目。工具是用户级、跨项目使用的，其他项目是否同形未测。

## 用户已定的事

1. 用途是**自己在 Claude Code 里用**，不是给 `backend/llm_client.py` 那套 agent 当工具层。
2. 目标是**降账单**，不是做一个像 dsh-ops 的东西。接受"dsh-ops 的一半能力 Claude Code 内置已有"这个事实，只补真空缺。
3. **范围收窄**：MCP 只做"把多次往返压成一次往返"。远程/SSH 执行**排除**在 MCP 之外，改用 CLAUDE.md 约定 + 一个脚本解决（换端口只改脚本一处，MCP 不保管任何凭据）。该脚本与那份凭据的存放方式**不属于本计划**，另立。
4. **批量工具的子操作可以包含 shell 命令**。
5. **授权姿态：注册时 always-allow，配一个服务器内策略层当刹车。** 用户已知悉这换来的是"一次批准 = 本会话内任意执行"，比内置 Bash 的按前缀匹配更宽。
   - 决策背景（不写会重蹈覆辙）：项目级 `.claude/settings.local.json` 已有 **999 条 Bash allow**，内置 Bash 实际已不弹窗。因此"每次调用人工确认"在现状下是空选项——要么第一次就被点成"不再询问"（等价于 always-allow 但没有策略层），要么一直拒绝导致工具弃用。用户先选了每次确认，看到这个事实后改为本方案。
6. **采纳**：在**用户级 CLAUDE.md** 写一条强指令，要求探索类操作优先走 `ops_batch`；验收时区分"被规则驱动"与"自发采用"。
7. **v1 的子操作严格扁平**，不支持串联。
8. **验收做受控 A/B**（见"成功判据"）。

## 目标

一个 stdio MCP 服务器，对外只暴露**一个**工具：

**`ops_batch`** —— 一次调用接受一个有序的子操作列表，按序执行，返回**一份**有界、按子操作分节的文本结果。

子操作种类：

| op | 参数 | 作用 |
| --- | --- | --- |
| `bash` | `command`, `cwd?`, `timeoutMs?` | 执行命令 |
| `read` | `path`, `offset?`, `limit?` | 读文本范围 |
| `grep` | `pattern`, `path?`, `glob?`, `outputMode?`, `caseInsensitive?`, `lineNumbers?` | 搜索 |
| `glob` | `path`, `pattern[]` | 找路径 |

每个子操作可声明自己的 `maxChars` 预算。

外加一个**服务器内策略层**，只作用于含 shell 的子操作。

## 非目标

- 不做 SSH/远程执行。
- 不把 read/grep/glob/edit 做成**独立**工具。它们与内置工具正面竞争必输，只作为 batch 的子操作存在。
- 不做后台任务（内置 Bash 已有 `run_in_background`）。
- v1 不做会话结果暂存区（dsh-ops 的 `ops_result`）。见"我的判断"。
- 不做跨宿主可移植性，不发布到任何市场。

## 反目标（技术上能跑但依然算失败）

- **模型不用它。** 一个没人调用的工具省不下任何东西。这是头号风险。
- 它退化成一个更差的 Bash。
- 它自身引入的延迟或报错导致模型重试，净收益为负。
- **静默截断**导致模型重跑命令来拿全量——比不截断更贵。
- **策略层被当成安全边界宣传。** 它不是，见下。

## 策略层：是刹车，不是边界

必须按这个定位写实现与文档，否则会制造虚假安全感。

- **拦什么**：明显毁灭性的模式（`rm -rf` 类递归删除、`mkfs`/`dd` 写块设备、`format`）与**写工作区外路径**的企图。
- **命中时**：该节返回 `status: rejected` 与理由，并在理由里明确告诉模型"若确实需要，请改用内置 Bash 单独执行"——把决定权交回给人，而不是让模型想办法绕。
- **可被绕过，且这是设计内的**：模型可以改用内置 Bash，或用变形命令规避模式匹配。**目标是防手滑，不是防对抗。** 任何把它描述成安全边界的措辞都要删掉。

## 约束

- Windows 11，shell 是 Git Bash。Python 3.13 与 Node 24 均可用。
- 必须能通过 Claude Code 的 MCP 配置注册并实际被调用。
- stdio 传输，每个 Claude Code 会话一个进程。
- 不打印凭据；工具输出里不得出现密钥（见"我的判断"，这是一条编码约定而非运行时模块）。
- 工具描述必须让模型**主动选择**它——这是采纳率约束，与实现同等重要。

## 我的判断（不是用户已同意的决定，builder 可推翻）

- **语言**：Python 3.13 + 官方 `mcp` 包，stdio。理由：这个项目整套工具链是 Python，出问题用户能自己读。
- **v1 砍掉 `ops_result`**：22 个会话里超过 60K 字符的结果一个都没有，为不存在的规模建分页协议不划算。改用**溢出到文件**（见下）。
- **代码位置**：`D:\guet-agent-微调\ops-mcp\`，在**用户级**注册（对所有项目可用）。
- **命名**：`ops_batch`。日后若证据支持再补 `ops_result`。
- **密钥约束的实现程度**：只做**编码约定**——服务器自己绝不打印它持有的凭据、绝不把 `env` 回显进输出。**不做输出扫描与改写**：扫描会误伤正常输出（长 base64、`.env` 里的普通值），直接撞上"报错导致重试"这个反目标。
- **状态与 cwd**：**跨调用无状态**（只留溢出文件）。一次 batch 内所有子操作共享一个 cwd，默认取服务器进程的工作目录。不做"cd 之后下次调用还在那儿"——那会让工具行为依赖不可见的历史，在用户级注册、多项目共用同一服务器进程时更危险。
- **溢出文件位置**：落在**工作目录内** `<cwd>/.ops-spill/`。原方案放系统临时目录是错的——工作目录之外内置 Read 会弹权限提示甚至被拒，会把"模型多一次调用"变成"模型重跑命令"，正是要避免的静默截断后果。

## 行为约定（已定的部分）

- **执行**：严格按序，串行，子操作之间**不共享数据**（不引用彼此的结果）。`stopOnError`（默认 false）决定首个失败后是否继续。
- **结果形态**：一个 text block，按子操作分节，每节带序号与一句头信息（op 类型、目标、耗时、是否截断、是否被策略层拒绝）。
- **错误以值返回，不抛异常**（沿用 dsh-ops 的契约）：某节失败就在该节写出 `status: failed` 与输出，其余各节照常。模型能看出是**哪一节**坏了，而不是收到一个笼统的调用失败。
- **截断**：超出该节预算时，把完整输出落到 `.ops-spill/`，节内给出预览、总行数/字符数与文件路径，并**显式标注被截断**。
- **超时**：每个 `bash` 子操作独立超时，默认值与上限由 builder 定。

## 成功判据（受控 A/B）

从历史 22 个会话里挑 **N 个有代表性的任务**，同一批任务在不同配置下各跑一遍。三个臂：

| 臂 | 配置 | 回答什么 |
| --- | --- | --- |
| 基线 | 不装 ops_batch、无规则 | 现状 |
| 装配无规则 | 装 ops_batch，不加 CLAUDE.md 指令 | **自发采纳** |
| 装配有规则 | 装 ops_batch，加 CLAUDE.md 指令 | **被规则驱动的采纳** |

**测量（成功判据）**

1. **往返次数**：单位工作量（折算到每个任务）下的工具调用次数。
2. **模型写入量**：工具参数字符总量——这是最贵的一档。
3. **采纳率**：`ops_batch` 被调用的次数与占比；自发臂与规则臂分开算。

**仪器**：`audit_transcripts.py`（目前只存在于临时目录，须落盘）。它既是本设计的复现手段，也是验收仪器。

任何一项不达预期，就是设计需要改，而不是"用起来就好了"。
